### 3-3. 데이터 검증 스크립트 3개

JSON 구조와 정합성만 보는 정적 검증이다. AI 응답, 브라우저, DB의 실제 동작을 검증하지 않는다.

| 스크립트 | 수정 전 | 경로 수정 후 |
|---|---|---|
| `data/validate_story_outlines.py` | **52/52 통과** | 변경 없음 |
| `data/cloud_data/tests/validate_cloud_chat_data.py` | **0/8 실패** (경로 오류) | **79/79 통과** |
| `data/fridge_data/tests/validate_fridge_data.py` | **0/10 실패** (파일 없음) | **112/112 통과** |

**발견한 문제.** 구름섬·냉장고 검증 스크립트는 입력 파일을 `데이터 루트/data/persona/...`처럼 찾는다. 현재 저장소는 `data/cloud_data/persona/...`, `data/fridge_data/persona/...` 구조라서, 그대로 실행하면 `data/data/...`를 찾다가 파일 없음으로 실패했다. 데이터 내용 문제가 아니라 스크립트의 경로 가정이 현재 구조와 맞지 않았던 것이다.

**대응(사용자 승인 후 수정).** 두 스크립트만 고쳤다.
- 기본 루트를 `parents[2]`(`data/`)에서 `parents[1]`(작품 폴더)로 바꾸고, 파일을 열 때만 `"data/"` 접두사를 제거한다(`removeprefix("data/")`).
- JSON이 서로 참조하는 논리 경로(`data/ending/...` 등)와 검사 항목은 그대로 둬서 검증 내용은 바뀌지 않았다.
- 안내 문구의 실행 경로도 현재 위치로 맞췄다. 냉장고의 `--root`는 이제 작품 폴더를 가리킨다.
- 수정 후 저장소 루트와 `data/` 폴더 양쪽에서 인자 없이 실행해 79/79, 112/112 통과를 확인했다. 수정 전 별도 경로 설정으로 얻은 값과 같다.

**참고: `AGENTS.md`의 80항목 기록.** `AGENTS.md`(11-15 항목, 커밋 `799bd00`으로 반영)에는 구름섬 검증이 80항목으로 적혀 있다. 이번 실행은 79항목이다. 다음을 확인했다.
- 스크립트는 최초 커밋(`65097bf`)부터 지금까지 내용이 동일하다(`git diff -M`에서 이름 변경만 있고 내용 변경 0줄, 이번 경로 수정 전 기준). 검사 항목 수는 데이터 길이에 따라 달라지지 않는다.
- 최초 커밋의 원래 폴더 배치(`data/data/tests/`)에서 실행해도 79/79, 11-17 커밋(`799bd00`) 시점 데이터와 이번 경로 수정본으로 실행해도 79/79다.
- 따라서 "과거 스크립트 버전의 집계 방식 차이"로는 설명되지 않고, 스크립트에서 항목이 누락된 흔적도 없다. 11-15에 80으로 기록된 실행은 커밋되지 않은 로컬 변형본이었거나 기록 오류였을 가능성이 있으나, 이를 재현하거나 확인할 근거는 찾지 못했다. **80항목 기록의 원인은 미확인이며, 현재 기준값은 79다.**

### 5-2. 11-18 CLI 10턴 상세

실행 조건: `GEMINI_HTTP_ATTEMPTS=1`, `STORY_GENERATION_ATTEMPTS=2`, 턴 사이 5초 대기, `responseJsonSchema` 사용. 각 작품 1회 실행한 결과이며 통계적 검증이 아니다.

| 작품 | 생성 호출 | 응답 제어 위반 | 형식 오류 | 비고 |
|---|---|---|---|---|
| 냉장고 | 10회 | 1건: 8턴 `too_many_sentences sentences=4` → 교정 재시도로 통과 | 0 | 지문 표기 정규화 1회 |
| 구름섬 | 9회 | 0 | 0 | 교정 재시도 없음 |

### 5-3. 실패 사례: 타임아웃과 503

이 사례들은 실제로 발생한 실패이며 발표 질의응답에서 투명하게 설명할 수 있어야 한다.

**(a) 읽기 타임아웃 (11-17, `gemini-3.5-flash`)**
- 증상: 냉장고 첫 턴 생성 요청이 HTTPX 읽기 제한 30초에 도달해 실패. 유효 응답 0건.
- 같은 키로 모델 메타데이터 조회는 성공(200)했고 DNS·TLS도 정상이어서 기본 연결 문제는 아니었다. **30초 지연의 원인은 확정하지 못했다**(기록상 "미확정").
- 대응: 읽기 타임아웃에서는 자동 재전송하지 않도록 유지. 추론 수준 `GEMINI_THINKING_LEVEL` 옵션, 응답 헤더·본문 구간 로그(`phase=before_headers`/`response_body`)를 추가. 11-18 검증에서 응답이 9~42초 걸린 점을 근거로 시연 시 `LLM_TIMEOUT_SECONDS=60`을 안내했고, 설정값이 HTTP 읽기 제한에 반영되는 것을 확인했다(30.0 → 60.0).
- Google이 `gemini-3.5-flash` 모델 ID의 생성 요청을 3.6 Flash로 라우팅한다고 안내하는 점을 문서에 기록했다. 앱은 모델 ID를 자동 변경하지 않는다.

**(b) HTTP 503 (11-17, `gemini-3.5-flash-lite`)**
- 증상: 응답 헤더 9.0초 후 Google HTTP 503. 앱에서는 HTTP 502로 변환되어 화면에 오류가 표시되었고, Mock 응답으로 대체되지 않는 것을 확인했다. 재시도·모델 자동 전환·임베딩 호출은 없었다.
- 대응(커밋 `bcbdab3`, `fb4c54d`): 공급자 503을 `gemini_unavailable` 503으로 전달하고, 화면에 "일시적으로 응답할 수 없음" 안내와 **15초 쿨타임**이 있는 다시 시도 버튼을 표시한다. 재시도는 같은 요청 ID를 쓰므로 실패한 턴은 저장되지 않고 성공한 턴만 한 번 저장된다. 429는 `Retry-After`만큼, 504·502는 즉시 재시도할 수 있고, 재시도로 해결되지 않는 오류는 '새로 시작' 버튼을 표시한다. 5xx는 시도마다 상태·코드·재시도 힌트만 로그에 남기고 프롬프트·사용자 입력·키는 남기지 않는다.
- 이 정책의 검증 근거는 **자동 테스트**(이번 신규 실행에 포함된 프론트 503 쿨타임·재시도 테스트 4건, 백엔드 `test_gemini_quota`·`test_gemini_server_error_log`)다. 실제 Google 503 상황에서 새 UX를 화면으로 확인한 기록은 찾지 못했다(§6).

**(c) 429(할당량)**
- 일일 한도 또는 판단할 수 없는 한도의 429는 자동 재시도하지 않고, 확인된 분당 한도만 제한된 횟수와 대기 시간으로 재시도한다. 대기가 15초를 넘으면 클라이언트에 반환한다. 실제 429가 발생한 사례 기록은 이번에 확인한 문서에 없고, 가짜 응답 테스트로만 검증했다.

### 9-4. 이번에 확인한 운영 주의 [신규 확인]

- `backend/.env`의 `SECRET_KEY`가 관리자 인증 조건(32자 이상, 기본값 불가)을 통과하지 못한다. 그대로 서버를 띄우면 관리자 로그인이 503이다. 시연 전에 교체해야 한다. → 11-22 값이 비어 있던 것을 확인하고 64자 무작위 값으로 교체했다(`.env`는 커밋 대상 아님).
- `FRIDGE_QWEN_DIALOGUE_ENABLED=true`가 `.env`에 켜져 있다. 이 상태의 냉장고 응답은 Qwen 연결에 의존한다.
- 로컬에 포트 8000 서버가 이미 실행 중이었다. 이번 검증은 그 서버를 건드리지 않고 8001에서 진행했다.

### 9-5. 아직 검증하지 않은 항목

### 10-2. 실패를 흉내 낸 서버 [신규 실행]

- 구성: 로컬 가짜 Gemini(`GEMINI_BASE_URL`을 로컬로 지정, 가짜 키)와 임시 SQLite, `FRIDGE_QWEN_DIALOGUE_ENABLED=false`. 외부로 나간 요청은 없다.
- HTTP: 가짜 Gemini가 503·429·형식 오류를 번갈아 응답하도록 하고 두 작품 10턴(자유 입력·선택지 교대)을 진행했다. 1~9턴 모두 200·`provider=fallback`, 10턴 `provider=fixed`, 같은 요청 ID 재전송 `replayed=True`, 결말 냉장고 `fridge_rel_stage_2`·구름섬 `cloud_result_toto`. 503은 공급자가 1회 재시도하면서 다음 429를 받아 이 실행의 사유는 모두 `provider_quota_unknown`이었다.
- 브라우저(`VITE_STORY_CLIENT=api`): 503 두 번·형식 오류 두 번을 번갈아 응답하도록 바꿔 두 작품을 결과 화면까지 진행했다. 서버 로그 사유는 `provider_http_503`과 `response_control:format,format`이 번갈아 나왔다. 오류 화면·다시 시도 버튼·콘솔 오류 없이 고정 대사가 일반 말풍선으로 표시되었고, 개발 빌드 배지에만 `provider=fallback`이 보였다.
