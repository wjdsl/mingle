## 구현 범위

- 개강 2턴: 선택지와 300자 자유 입력 → 사용자 메시지 → 지연된 Mock 응답 → 진행·감정 갱신.
- 모바일·데스크톱 모두 최대 430px의 동일한 세로형 한 열 화면.
- 전체 화면은 뷰포트 높이에 맞춘다. 시작·에피소드·유저노트·앨범·엔딩 카드에 수동 화면 스크롤 없이 접근하도록 이미지와 여백을 남는 높이에 맞춰 배치한다. 낮은 높이에서는 장식 문구·도장을 줄인다. 채팅 목록의 최신 메시지 자동 스크롤은 유지한다.
- 채팅 선택지와 입력 안내의 장식 화살표를 제거했다. 전송 버튼은 유지한다.
- 시작 화면(로고·제목·게임 시작) → 개강 에피소드 소개(큰 캐릭터·진입 버튼) → 채팅 순서다. 에피소드 소개는 대화 턴마다 반복하지 않는다.
- 채팅 상단에는 진행 바와 유저노트·엔딩 도감 아이콘만 두고, 남은 공간을 대화 목록이 채운다. 새 메시지·응답·화면 크기 변경 시 최신 메시지로 자동 스크롤한다. 수동 스크롤은 과거 대화 열람을 위해 유지한다.
- 코믹 미연시 UI: 큰 캐릭터 소개 영역을 채팅에 복구하지 않고 캐릭터 메시지 옆에 기존 감정 PNG를 배치한다. 메시지별 감정을 보존하고 최신 응답에서만 1회 리액션을 표시한다. `또각` 대사는 별도 코믹 말풍선 스타일을 사용한다. 선택지는 hover·focus·active·선택함 상태를 구분한다.
- `useViewportHeight`는 Visual Viewport 변경을 구독한다. 가용 높이가 560px 이하이면 선택지를 가로 묶음으로 표시하고 장식 라벨을 줄여 입력 공간을 확보한다. 실기기 키보드 동작을 검증 완료한 것은 아니다.
- 유저노트 아이콘은 빈 상태 화면으로, 엔딩 도감 아이콘은 졸업 앨범 화면으로 이동한다. 돌아오면 입력문·대화·진행을 유지한다. 실제 기억 추출·저장 및 엔딩 판정·획득은 구현하지 않았다.
- 도감은 종이 앨범·제본 고리·테이프 사진 카드 그리드로 표현한다. 내 앨범은 획득 0개·전체 잠금 상태다. 4칸은 배치 예시이며 최종 엔딩 개수가 아니다. 미획득 엔딩명·이미지·조건은 노출하지 않는다.
- `디자인 샘플` 모드에서는 획득 카드 예시 1개를 비교할 수 있다. 샘플 카드나 `엔딩 카드 디자인 미리보기`에서 졸업 기념 엔딩 카드(U06)를 확인할 수 있다. 실제 획득·저장은 발생하지 않는다. MD §6.2의 카드 구조와 §6.3의 졸업 앨범을 바탕으로 디자인했다.
- 샘플은 PM 기획서 v0.2 §6.1의 후보 `종강 생존 푸르마` 문구를 사용한다. 최종 엔딩 확정을 의미하지 않는다. 저장·공유는 후속 구현 대상이다.
- 빈 입력·한글 조합 Enter·중복 전송·오류 재시도·재시작 처리.
- 메모리 상태만 사용. 새로고침하면 초기화하며 입력·통계를 서버로 전송하지 않는다.
- 실제 LLM·서버·6구간 전체·스탯·엔딩 판정·도감 획득 저장·인증·영구 저장·운영용 안전 검출은 미구현.
- 프로젝트 전체 설계의 캐릭터 선택 화면은 후속 범위이며 이번에는 시작·에피소드 소개를 거쳐 푸르마와 대화한다.

## 2026-11-22 진행 저장·결말 도감·결과 이미지 (냉장고·구름섬)

위의 "새로고침하면 초기화" 설명은 이 절 이전 상태다. 푸르마도 2026-11-22 푸르마 10턴 절부터 같은 방식으로 저장한다.

- **진행 저장·이어하기** (`services/storyProgress.ts`): 이 기기의 `localStorage`(`mingle.progress.v1.<작품>`)에 호칭, 완료한 장면 수, API 모드의 개인 코드·대화 ID만 저장한다. 대화 원문은 저장하지 않는다. 실행 모드(mock / scenario-mock / api)가 다르면 다른 기록으로 본다. 작품 소개에 "이어하기 / 새로 시작", 홈 카드에 "이어서 하기" 표시가 나온다. 이어하기는 현재 장면의 첫 대사부터 다시 보여 준다.
- **API 모드 이어하기**: 서버 `GET /api/story-chat/conversations/{id}`로 진행 장면을 먼저 확인한다. 서버 기록이 없거나 끝났거나 확인에 실패하면 저장 기록을 지우고 "이전 기록을 이어갈 수 없어 처음부터 시작해요"로 새 대화를 시작한다.
- **결말 도감** (`services/endingCollection.ts`, `StoryCollection.tsx`): 냉장고 관계 결말 3칸, 구름섬 대원 타입 5칸. 얻은 결말 ID만 `mingle.endings.v1`에 저장하며 다시 시작해도 유지한다. 결말 판정이 아직 없어 `recordEnding`을 부르는 곳이 없고 모든 칸이 잠겨 있다. 고정 샘플 결과는 획득으로 기록하지 않는다.
- **결과 이미지 저장** (`services/resultImage.ts`): 결과 카드를 canvas로 그려 1080×1350 PNG로 내려받는다. 호칭은 넣지 않고, 고정 샘플 안내 문구와 구름섬 '결과 예시' 표시는 이미지에도 남긴다. 새 의존성 없음.
- 보관 기간은 기획서 미결정 1번이라 만료를 두지 않았다.

## 2026-11-22 메신저 미리보기 카드 (공유 링크)

카카오톡·디스코드 등에 공유 링크를 붙이면 주소 대신 이미지·제목·소개가 담긴 카드가 보이도록 Open Graph·Twitter 카드 메타 태그를 넣었다. 새 의존성은 없다. 카카오톡 전용 공유 API(앱 키 필요)는 범위에서 뺐다.

- **공유 링크 형식**: `<배포 주소>/share/<작품ID>/?from=share` (`puruma` / `fridge` / `cloud`). 메신저는 주소의 `#` 뒤를 읽지 않아서 작품마다 정적 공유 페이지를 둔다. 이 페이지는 메타 태그만 갖고 있다가 브라우저에서는 곧바로 `/?from=share#/project/<작품ID>`(작품 소개 화면)로 넘어간다. 그래서 공유 유입 통계(`link_open`·`link_start`)는 예전과 같이 기록된다. 링크에는 작품 ID와 공유 유입 표시만 넣고 호칭·대화·결과는 넣지 않는다.
- **사이트 기본 카드**: 홈 주소(`index.html`)에도 메타 태그가 들어간다. 기존 `description`("Mock 프로토타입" 문구)은 카드 소개 문구로 바뀌었다.
- **코드 위치**: 카드 문구·공유 주소·공유 페이지 HTML은 `src/share/shareCards.ts` 한 곳에 있다. 작품 제목·소개는 `catalog.ts`와 같아야 하며 `tests/shareCards.test.ts`가 확인한다. `vite.config.ts`의 `mingle-share-preview` 플러그인이 `index.html`에 메타 태그를 넣고, 빌드 결과에 `share/<작품ID>/index.html`을 만들고, 개발 서버에서도 같은 주소를 연다.
- **미리보기 이미지**: `public/og/`의 1200×630 JPG 4장(`site`·`puruma`·`fridge`·`cloud`). 원본 에셋(`assets/cloud/sky-islands.webp`, `assets/fridge/fridge-smug.webp`, `assets/puruma/happy.png`)을 배치한 화면을 헤드리스 Chrome으로 찍어 새로 만들었다. 원본은 수정하지 않았다. 사이트 카드는 세 작품을 나란히 보여 준다.

### 배포 주소 환경 변수 `VITE_SITE_URL`

메신저는 메타 태그의 이미지·주소가 절대 주소여야 읽는다. 빌드할 때 배포 주소를 넣는다. 하위 경로에 배포하면 그 경로까지 넣는다.

```bash
VITE_SITE_URL=https://배포-주소 npm run build
```

- **값이 있으면**: `og:image`·`twitter:image`가 `https://배포-주소/og/<이름>.jpg`, `og:url`이 `https://배포-주소/share/<작품ID>/`(홈은 `https://배포-주소/`)가 된다.
- **값이 없으면**: 빌드는 그대로 되지만 경고가 한 줄 나온다. 이미지 주소가 `/og/<이름>.jpg` 같은 상대 경로로 들어가고 `og:url`은 빠진다. 이때 메신저 카드에는 제목·소개만 나오거나 이미지가 빠질 수 있다. 개발 서버(`npm run dev`)와 로컬 확인에는 영향이 없다.
- 공유 버튼이 만드는 링크 자체는 `VITE_SITE_URL`이 아니라 지금 열려 있는 주소(오리진 + 기본 경로)를 쓴다.

### 배포 후 확인할 것

- 실제 메신저(카카오톡·디스코드 등)에 링크를 붙여 카드가 보이는지는 아직 확인하지 않았다. 배포 주소가 생기면 확인한다.
- 카카오톡은 한 번 읽은 카드를 캐시한다. 이미지나 문구를 바꾼 뒤에는 카카오 개발자 사이트의 공유 디버거로 캐시를 지워야 새 카드가 보인다.
- 정적 호스팅에서 `/share/<작품ID>/`가 `share/<작품ID>/index.html`을 돌려주는지 확인한다. 끝 슬래시 없는 주소(`/share/fridge`)를 슬래시 주소로 넘기는 처리는 개발 서버에만 있다. 공유 버튼은 항상 끝 슬래시를 붙인다.

## 2026-11-22 AI 실패 시 고정 대사 진행 (냉장고·구름섬 API 모드)

- 서버가 AI 실패(503·429·시간 초과·응답 검증 실패) 때 장면 고정 대사로 응답하면(`provider=fallback`) `apiStoryClient.ts`는 일반 응답과 똑같이 진행한다. 말풍선에 별도 표시는 없고, 개발 빌드의 좌하단 배지에만 `provider=fallback`이 보인다. 그 밖의 공급자 불일치는 기존처럼 오류다.
- 그래서 Gemini 503 대기(15초)·다시 시도 버튼은 서버가 대체할 대사가 없는 예외적인 경우에만 나타난다. 서버에 연결하지 못하는 네트워크 오류는 기존처럼 오류 안내와 다시 시도를 표시한다.

- **실행 모드** (`VITE_PURUMA_CLIENT`)
  - `mock`(기본, `npm run dev`): 브라우저 Mock. 고정 반응만 보여 주고 스탯·홍보·엔딩 판정은 없다. 결과는 디자인 샘플 카드다.
  - `scenario-mock`(`npm run dev:puruma-scenario-mock`): 서버 Mock(백엔드 `LLM_PROVIDER=mock`). 대사는 고정이지만 홍보 카드, CC 분기, 엔딩 판정은 서버 규칙으로 실제 동작한다.
  - `api`(`npm run dev:puruma-api`): 서버의 실제 Gemini. 10턴에 호출 10~20회.
- **서버 클라이언트**: `src/services/apiPurumaStoryClient.ts`가 `/api/story-chat`에 `project=puruma`로 대화를 만들고 매 턴 로컬 기억(`notes`)을 함께 보낸다. 응답의 `emotion`, `promo`, `notes`, `ending`을 쓴다. 같은 requestId 재시도는 서버가 저장된 응답을 돌려준다.
- **화면**: 진행 헤더는 구간과 10턴 진행을 보여 준다. 홍보는 대사 아래 링크 카드로 붙고 새 탭으로 열린다. 다 마치면 서버가 정한 엔딩 카드를 보여 주고 6칸 졸업 앨범에 기록한다.
- **진행 저장·이어하기**: 냉장고·구름섬과 같은 `storyProgress.ts` 형식(`mingle.progress.v1.puruma`)이다. 서버 모드는 서버 진행 턴을 먼저 확인하고, 기록이 없거나 끝난 대화면 처음부터 시작한다. 이어하기는 현재 턴의 첫 대사부터 다시 보여 준다.
