# 구름섬 구조대 — 채팅 데이터 설계서

## 1. 문서 개요

- 버전: **0.2 (2026-11-11, 데이터/검증 재검토)**
- 범위: 밍글 **모드 B 「닮은 인물 찾기」**의 채팅 데이터 구조 초안
- JSON 공통 `schema_version`: `0.2` (데이터 명세 버전이며 서비스 구현 버전은 아님)

- 본 문서는 **데이터 담당 산출물만** 설명한다. 백엔드/프론트/AI 소스와 푸르마 자료는 변경하지 않았다.

## 2. 추가 산출물

| 파일 | 내용 | 성격 |
|---|---|---|
| `data/persona/cloud_personas.json` | 토토·비비·나나·키키·두두 성격, 말투, 호칭, 지문, 금지 | 바이블 정리 |
| `data/rag/cloud_world_knowledge.json` | 구름섬·구조대·위험 지대의 공개 세계관 정보 | 창작 설정 참고 데이터(실제 외부 RAG 아님) |
| `data/rules/cloud_chat_rules.json` | 다중 발화, 지문, 스포일러, 개인정보, 장면 복귀 | 바이블+밍글 공통 요구사항 |
| `data/scenario/cloud_story_outline.json` | 5단계 흐름, 약 10턴의 **빈 슬롯** | 장면/선택/대사 미확정 |
| `data/rules/cloud_trait_axes.json` | 관계↔목표 / 안정↔도전 축, 캐릭터 매핑, 채점 범위 | 수치 배정·중앙값 미확정 |
| `data/ending/cloud_result_types.json` | 닮은 대원 5종과 결과 카드 **가안** | 결과 문구 미확정 |
| `data/state/cloud_state_schema.json` | 로컬 저장할 진행 상태 필드 예시 | **구현 제안**, API 계약 아님 |
| `data/tests/cloud_chat_test_cases.json` | 대화·스포일러·안전 등 20개 행동 테스트 | **미실행 테스트 명세** |
| `data/tests/validate_cloud_chat_data.py` | 필수 필드·자료형·파일 간 참조·핵심 기획값 정적 검증 실행 | 실제 JSON 검증 도구 |

### 파일별 주요 필드

| 파일 | 최상위 주요 필드 | 연결 관계 / 데이터 사용 시 주의 |
|---|---|---|
| `cloud_personas.json` | `personas[]` (`id`, `name`, `speech`, `forbidden`, `result_type_id`) | `result_type_id`는 결과 카드 ID 참조. `speech.user_address`는 **호칭 목록**, 두두의 첫 호명 시기는 별도 필드 |
| `cloud_world_knowledge.json` | `allowed_facts[]`, `excluded_answer_topics[]` | 공개·비공개 설정을 구분. 외부 정보 검색용 RAG가 아닌 창작 세계관 참고 데이터 |
| `cloud_chat_rules.json` | `priority_order`, `user_role`, `per_turn`, `input`, `story`, `content_safety`, `promotion`, `error_fallback` | 모든 캐릭터 공통 행동 규칙. 실제 안전 감지/스포일러 차단/오류 대체 기능은 별도 구현 |
| `cloud_trait_axes.json` | `axes[]`, `per_free_input_score_bound`, `choice_scores`, `result_quadrants[]` | 선택지 점수·중앙 경계·동점 처리 등이 `null`: 현재 자동 결과 판정 불가 |
| `cloud_story_outline.json` | `phases[]`, `turn_slots[]`, `post_cliffhanger` | `turn_slots[].phase_id` → `phases[].id`. 턴별 장면·선택지 등은 `null` |
| `cloud_result_types.json` | `result_cards[]` (`result_type_id`, `character_id`, `title`, `description`) | 각 카드가 대원과 1:1 연결. 문구는 가안이고 실제 이미지 승인 미확정 |
| `cloud_state_schema.json` | `storage_policy`, `fields[]` | 브라우저 저장용 **필드 제안**, 현재 구현 타입·DB 스키마가 아님 |
| `cloud_chat_test_cases.json` | `cases[]` (`id`, `category`, `input_or_situation`, `expected_behavior`, `status`) | 검증 요구사항 20개를 정의한 것으로, 자동 수행 테스트가 아님 |

`project_id`는 전 파일에서 `cloud`를 사용하며, 각 `id`/`result_type_id`/`phase_id`/`turn_id`는 v0.2 데이터 파일 간의 **참조 규격 초안**이다. 다른 프로젝트나 백엔드의 확정 API ID라고 해석하지 않는다.

## 3. 핵심 설계 판단

**푸르마의 스탯·친밀도 규칙을 재사용하지 않는다.** 구름섬은 다섯 캐릭터가 한 턴에 최대 세 명 발화하며, 최종 결과가 두 개의 성향 축에 의해 결정되는 별개의 이야기다.

### 말하기 및 사용자 처리

- 모든 대원은 반말, 지문은 캐릭터마다 한 턴에 괄호 한 줄까지다.
- 대원의 개인 말투와 금지 규칙은 `cloud_personas.json`, 전체 우선 규칙은 `cloud_chat_rules.json`으로 나눈다. **두두의 `speech.user_address`는 `{nickname}`만 담고, 첫 호명 단계는 `speech.nickname_first_mention_phase_id=cloud_phase_teaser`로 별도 명시한다.**
- 사용자는 임시 승무원이다. 실명·학교·연락처를 수집하거나 되풀이하지 않는다. 의심 닉네임은 `신입 대원`으로 대체한다. **구체적인 식별 로직은 미정**이다.
- 자유 입력은 **그 턴의 확정된 선택지**에 가까운 의도로 분류한다. 현재 공식 선택지/점수가 없으므로 선택 ID를 임의 생성하지 않는다.

### 성향 점수 및 결과

- 두 축은 `관계·공감(-) ↔ 목표·효율(+)`, `안정·안전(-) ↔ 도전·변화(+)`다. 축 방향은 공식 그림에서 확인했다.
- **공식 확정:** 자유 입력의 축별 점수 범위 `-2~+2`; 토토(목표·도전), 비비(목표·안정), 나나(관계·안정), 키키(관계·도전), 두두(중앙).
- **미확정:** 각 고정 선택지의 점수, 자유 입력의 세부 점수 기준, 초기 점수, 축 경계·동점 처리, 두두 중앙 허용 범위. `null`로 보존했다.
- 결과 문구 5개는 스토리 바이블의 **가안**을 그대로 가져왔다. 비비 타입명은 기획 재확인 필요.

### 장면·홍보 및 안전

- 공식 바이블의 5단계(합류 1–2 / 출동 3–4 / 위기 5–6 / 구조 7–9 / 예고편 컷 10)를 **초안**으로 저장했다.
- 10턴에 실제 결말을 만들지 않는다. 검은 하늘·그림자·나침반은 정체를 설명하거나 추측하지 않는다.
- 홍보 위치/버튼 문구는 바이블에서 확인했으나 **본편 URL은 미정**이다. 임의 URL은 없다.
- 위기 신호에 대한 공식 안내 문구는 별도 합의가 필요하다. 특정 상담 연락처를 임의로 만들지 않았다.
- SRS FR-63에 따른 욕설·혐오, 연애·성적 요구 대응 규칙을 추가했다. FR-65의 AI 응답 오류 대체 기능은 **필요 조건만 명시**하고 실제 대체 대사(`null`)와 구현은 미확정이다.
- 홍보 콘텐츠 닫기 후 동일 진행 중 재노출 금지(FR-32)를 명시했다. 노출 판단 로직은 구현되지 않았다.

### 사용자 진행 상태와 도감

- `cloud_state_schema.json`은 **브라우저 로컬 저장 상태의 논리 필드 제안**이다. 특정 백엔드 모델이나 프론트 타입을 확정하지 않는다.
- SRS FR-44/45에 맞춰 `obtained_result_type_ids`(획득한 타입 목록)를 제안했다. `result_type_id`(이번 실행 결과)와 분리되며 **다시 시작해도 도감은 유지**해야 한다. 실제 저장 키와 복원·만료 정책은 미확정이다.
- SRS FR-52 User Note 자체는 전체 서비스 공통 요구사항이다. **구름섬 전용 User Note 세부 규격은 아직 확정되지 않아 파일을 새로 만들지 않았다.** 개인정보 원문 저장 규칙을 임의 확장하지 않는다.

## 4. 기존 코드와의 관계

| 현황 | 확인 내용 | 데이터 측 처리 |
|---|---|---|
| `frontend/src/projects/stories/catalog.ts` | 구름섬이 3개 미션 및 고정 나나 결과 카드로 구성된 **Mock** | 공식 10턴 데이터가 구현된 것으로 간주하지 않음 |
| 동일 파일 키키 역할 | 화면에 '호기심 많은 발명가'라고 표시 | 정본 바이블은 **키키=사고뭉치 / 비비=발명가 겸 정비**. 프론트 담당 확인 필요 |
| `backend/app/services/persona_prompt.py` | 단일 페르소나 관계 단계·호감도 기반 프롬프트 | 구름섬의 5인 동시 발화·2축 성향 연동을 지원한다고 단정할 수 없음 |
| `backend/app/services/conditions.py` | 친밀도/신뢰도 등의 조건 키 존재 | 구름섬 성향 축 전용 조건을 구현한 것으로 간주하지 않음 |

**이 파일들은 신규 데이터 명세일 뿐, 현재 백엔드·프론트 화면에 자동으로 연결되지 않는다.** API 계약과 실제 사용 필드명은 담당자 간 합의가 필요하다.

## 5. 검증

프로젝트 루트에서 실행:

```bash
python data/tests/validate_cloud_chat_data.py
```

이 스크립트는 파일 읽기 및 JSON 파싱, 필수 필드·자료형, ID 중복과 참조, 캐릭터 5종·결과 카드 5종의 1:1 대응, 단계·턴 번호, 성향 점수 범위와 결과 매핑 등의 **정적 정합성**만 검사한다. v0.2 기준 정상 데이터에서 **79/79 통과**했다. LLM 품질, 안전 응답의 실제 성능, AI 분류 정확도, DB 연동, 브라우저 저장은 평가하지 않는다. 행동 테스트 20개는 미래의 통합 평가용이다. 검증기의 실패 처리 자체도 문법 오류, 필수 필드 누락, 잘못된 결과 참조·성향 매핑, 두두 호명 단계 오류, 초깃값 구조 오류, 단계 누락 등 **7가지 변형 사례에서 비정상 데이터를 실패로 탐지**하는지 별도로 시험했다. 이 시험은 실제 LLM 행동 검증과 별개다.

## 6. 기획 담당과 확인할 목록

1. 10턴의 실제 장면·발화 캐릭터·선택지·대사·반응
2. 선택지별/자유 입력별 점수 기준 및 중앙(두두) 경계·동점 규칙
3. 결과 카드 5종 최종 문구와 비비 타입명
4. 키키/두두 최종 이미지 확정 및 표시 자산 경로
5. 본편 연결 URL, 닉네임 검사 규칙, 위기 대응 문구
6. 프론트 3미션 Mock을 교체할 시점과 데이터 로딩/API 필드명
7. AI 응답 실패 시 공식 대체 대사, 안전 안내 문구 및 User Note 세부 규격
8. 도감 저장 키·복원/만료 정책, 홍보 노출 제한 구현 방식
